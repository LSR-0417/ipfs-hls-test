# Git Atomic Committer

產生符合 Atomic Commit 原則的 Git commit 訊息。先分析實際變更，再決定要輸出一條或多條 commit 訊息。

## 工作流程

1. 先讀取使用者提供的 `git diff`、`git status`、變更摘要或需求描述。
2. 若使用者沒有提供明確內容，優先檢查 `git diff --cached`，再檢查 `git diff` 與 `git status --short`。
3. 依「單一邏輯目的」分組變更，而不是只看檔案路徑或副檔名。
4. 判斷每一組變更是否能獨立回滾；可以獨立回滾的內容就拆成不同 commit。
5. 為每一組變更挑選唯一最貼切的 type，最後再撰寫描述。

## Atomic Commit 判斷準則

- 功能變更、重構、CI 調整、建置設定、文件整理若屬於不同目的，必須拆成多條 commit。
- 直接支援同一功能或同一 bug 修正的測試，可以和主變更放在同一條 commit；獨立的測試維護應拆成 `test`。
- 直接支援同一功能的文件更新，可以和主變更放在同一條 commit；純文件整理應拆成 `docs`。
- 只因順手一起改到、但不影響主要目的的內容，不要硬塞進同一條 commit。
- 若同一批修改很難用一句話描述成單一目的，代表應該拆分。

## Type 選擇規則

- `feature`: 新增功能，或調整既有功能行為。
- `fix`: 修正 bug、異常行為、邏輯錯誤或錯誤處理。
- `docs`: 新增或修改 README、設計文件、註解等說明內容。
- `style`: 只調整格式、排版、縮排、lint 修正等不影響邏輯的內容。
- `refactor`: 重構程式碼、抽共用邏輯、重新命名、重組結構，但不改變對外行為。
- `perf`: 改善效能、降低資源消耗、減少重複運算。
- `test`: 新增或修改測試案例、測試工具、測試基礎設施。
- `build`: 調整建置流程、套件版本、Dockerfile、編譯設定或外部依賴。
- `ci`: 修改 CI/CD 流程、工作流程腳本或自動化檢查設定。
- `chore`: 其他例行維護，例如清理未使用檔案、更新開發工具設定。
- `revert`: 撤銷先前 commit。

## 描述撰寫規則

1. 只輸出 `<type>: <description>`，不要加引號、項目符號、編號、句點、說明或前後文。
2. 一律使用台灣正體中文，避免簡體中文用語。
3. 優先使用台灣軟體界常見詞彙，例如 `程式碼`、`檔案`、`資料庫`、`伺服器`、`支援`、`預設`、`解析度`、`套件`、`部署`。
4. 不要使用 `代码`、`文件`、`数据库`、`服务器`、`支持`、`默认`、`分辨率`、`包` 等簡體寫法；若輸入含有簡體詞，仍要轉成台灣慣用詞。
5. 描述要直接說明變更目的，不要寫成空泛句子，例如避免 `fix: 修正 bug`、`refactor: 調整程式碼`。
6. 優先使用動詞開頭的短語，例如 `fix: 修正播放器切換字幕時的狀態重置`。
7. 只使用 `feature`，不要改寫成 `feat` 或其他變體。

## 輸出規則

- 只需要一條 commit 時，只輸出一行。
- 需要拆分多條 commit 時，每行輸出一條 commit 訊息，不要加 `-`、`*` 或數字編號。
- 不要補充你如何判斷、為何拆分、或任何額外解釋，除非使用者明確要求。

## 範例

輸入：
把 LLM Agent 的 API 呼叫邏輯拉出來重構了，順便更新了 GitLab CI 的 docker build 腳本，然後清掉專案裡沒有用到的測試設定檔。

輸出：
refactor: 提取 Agent API 呼叫的共用邏輯
ci: 更新 Docker 建置與部署腳本
chore: 清除未使用的舊有測試設定檔

輸入：
新增 HLS 播放器的字幕切換功能，並補上對應的單元測試。

輸出：
feature: 新增 HLS 播放器的字幕切換功能

輸入：
只調整 ESLint 排版規則，沒有改任何執行邏輯。

輸出：
style: 調整 ESLint 排版規則
